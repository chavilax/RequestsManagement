# החלטות טכנולוגיות, מגבלות ושימוש ב-AI

## שתי החלטות טכנולוגיות מרכזיות וחלופות שנשקלו

### החלטה 1: SQL Server + EF Core (לעומת MongoDB)

**הבחירה:** SQL Server עם Entity Framework Core.

**הנימוק:**
- **Optimistic Concurrency מובנה:** עמודת `rowversion` של SQL Server מתעדכנת אוטומטית, ו-EF Core מזהה עדכונים מתחרים דרך `DbUpdateConcurrencyException` — ללא קוד ניהול גרסאות ידני.
- **שאילתות מורכבות:** סינון דינמי לפי 6 שדות, מיון דינמי ו-Aggregations מתבטאים נקי ב-LINQ/IQueryable ומתורגמים ל-SQL יעיל.
- **אינדקסים גמישים:** אינדקסים מורכבים (כמו `(Status, CreatedAt)`) תומכים בסינון ומיון בו-זמנית.

**החלופה שנשקלה — MongoDB:** מתאים לנתונים לא-מובנים, אך Optimistic Concurrency דורש ניהול שדה גרסה ידני ו-`FindOneAndUpdate` מותנה. למבנה הטבלאי והיחסי של פניות + היסטוריה, SQL Server מתאים יותר.

### החלטה 2: Partial Success ב-Bulk Update (לעומת All-or-Nothing)

**הבחירה:** Partial Success — כל פנייה מטופלת בנפרד, התשובה מפרטת הצלחות וכשלונות.

**הנימוק:** בעדכון סטטוס ארגוני, כישלון של פנייה בודדת לא צריך לגרור ביטול של כל השאר. הלקוח מקבל תמונה מלאה ויכול לפעול על הכשלונות בלבד.

**החלופה שנשקלה — All-or-Nothing:** פשוט יותר לוגית (טרנזקציה אחת), ומתאים לפעולות פיננסיות שבהן עקביות מוחלטת קריטית. כאן הוא פחות שימושי בפרקטיקה.

> החלטה שלישית (Cache) מתועדת ב-[caching.md](caching.md): IMemoryCache לעומת Redis.

## אסטרטגיית Validation (שלוש שכבות)

הוולידציה מיושמת בשלוש שכבות משלימות, לפי העיקרון: **client לנוחות, server לאמינות**.

| שכבה | סוג | דוגמאות |
|---|---|---|
| **Client (Angular)** | מניעה | ה-UI מציג רק מעברי סטטוס חוקיים, הגבלת בחירת Bulk ל-100, כפתורים disabled בזמן שמירה |
| **FluentValidation** (WebApi) | מבנה הקלט | NewStatus בטווח ה-enum, RowVersion לא ריק, Bulk 1–100, אורך ChangedBy |
| **BL** (Business Logic) | כללים עסקיים | מעברי סטטוס מותרים, קיום פנייה, Optimistic Concurrency |

**הנימוק להפרדה:** ולידציית client לבדה אינה מספיקה — ניתן לעקוף אותה (Postman, קריאה ישירה ל-API), ולכן השרת **חייב** לאכוף. ה-client מספק UX טוב (מניעת קלט לא תקין מראש), FluentValidation תופס קלט פגום מוקדם לפני הלוגיקה, וה-BL אוכף את הכללים העסקיים העמוקים. ולידציית טפסים מפורטת (Angular Validators) לא נדרשה כי אין טפסי קלט חופשי מורכבים — רק בחירה מרשימות סגורות.

## מגבלה ידועה אחת ודבר אחד שניתן לשפר

**מגבלה ידועה:** ה-Cache (IMemoryCache) אינו עובד נכון בסביבה עם מספר מופעי שרת — כל מופע מחזיק cache משלו, ועדכון במופע אחד אינו מבטל את ה-cache באחרים. הפתרון (Redis) מתועד ב-[caching.md](caching.md), והקוד מוכן לכך דרך ה-abstraction `IStatsCache`.

**דבר שניתן לשפר:** החיפוש הטקסטואלי משתמש ב-`LIKE '%term%'`, שאינו יכול לנצל אינדקס רגיל (ראה [performance.md](performance.md)). על 100K הביצועים סבירים (~20ms), אך לכמויות גדולות יותר כדאי לעבור ל-Full-Text Search של SQL Server. לא יושם כעת כדי להימנע מ-Over-Engineering ביחס לדרישה.
